# Adversarial Review: Claude Sonnet 5 (multi-pass fork review), 2026-08-23
**Target:** design_docs/design-v12.md — `> **Status:** Authoritative (v12). One section is open: Wiring & construction.`
**Verdict:** Sound with fixes. Independent attack passes across state machines, failure paths, orderings/races, arithmetic/bounds & determinism, Rust realizability (including compiler-executed checks), evidence claims, and vocabulary/self-conformance found no CRITICAL defects — every phase/edge table, every latch/lifecycle automaton, every commitment-point/failure-path combination, and every generics/macro/serde realizability claim checked out under direct construction of adversarial witnesses, several confirmed by actually compiling and running the code. The one MAJOR finding is a real internal-consistency gap (`DET-RUN`/`DET-ENV` silently drop the trust preconditions their own governing axiom states), not a soundness failure — the underlying guarantee is coherent once A9 is supplied, it just isn't self-contained where the document's own rules say every ID should be. ## Findings

### CR-01 `DET-RUN`/`DET-ENV` omit A9's stated trust preconditions — MAJOR, confidence medium, omission
- **Text attacked:** A9: *"The Core introduces no choice of its own: under `TRUST-PURE` and `TRUST-SERIALIZE`, every Core-owned run output (A1) is a function of the build, the Application, its initial State, the configuration, and the trace."* `DET-RUN`: *"Within one Environment type: the same build (toolchain and full dependency set, `serde_json` included), Application, initial State, configuration, and trace reproduce the same handler calls, State transitions, Command intent, and Journal bytes through the last committed record, and exits equal in every Core-owned discriminant and Core-owned payload — equal outright when the Error values erased from the trace also correspond."* `DET-ENV` inherits via *"under `DET-RUN`'s premises."*
- **Claim:** A9 explicitly scopes Core determinism to hold "under `TRUST-PURE` and `TRUST-SERIALIZE`" — two Obligations-table rows, which per §0 are *trusted* (checked by a named party/means) rather than *enforced* (unrepresentable/asserted/tested). `DET-RUN`/`DET-ENV` sit in a Guarantees table, so §0 requires each to be enforced, yet neither row restates the qualifier its own axiom names as a precondition — read on its own, as §0's "cite IDs" discipline and the document's "stands alone" premise both invite, `DET-RUN` promises unconditional byte-for-byte reproducibility.
- **Witness:** An `Application::Command` payload derives `Serialize` over a `HashMap<String, V>` field — nothing in `type Command: Serialize` or any enforced rule forbids this; only `TRUST-SERIALIZE` (unenforced) asks for "stable map order." Two runs, identical build/Application/initial State/config/trace, insert the same keys via two code paths that iterate the map differently; `CommandsPrepared`'s `commands` field serializes in that order, so the two runs' Journal bytes diverge — directly falsifying `DET-RUN`'s literal text, even though the payload type violates no *stated* trait bound. Elsewhere the document cites exactly this kind of trust dependency inline where it matters (`JRN-SINK`: *"stores exactly the bytes given — the sink owner's obligation (`TRUST-SINK`)"*; Application Notes: *"Determinism then rests on State and the payload types carrying no hidden authority, which is the Application author's trusted obligation"*) — `DET-RUN`/`DET-ENV` are the two rows that break that convention where the omission is most consequential. (The only textual tie-back is oblique: `TRUST-PURE`'s own "Verified by" column mentions "`DET-RUN`-equal exits" as *its* check, not as `DET-RUN`'s own enforcement citation — see CR-05.)
- **Fix sketch:** Add "under `TRUST-PURE` and `TRUST-SERIALIZE`" to `DET-RUN`'s row text (`DET-ENV` inherits the fix via "`DET-RUN`'s premises").

### CR-02 `Quiescence`'s "witnessed complete" claim isn't actually witnessed for Sim or a bespoke Environment — MINOR, confidence medium, unenforceable claim
- **Text attacked:** Glossary: *"**Quiescence** — whether all run-scoped activity finished: `Quiesced` (witnessed complete) or `Incomplete`."* Commitment-points table, `shutdown` row: *"`Quiesced` witnesses that every unit of run-scoped activity completed."* `SIM-SHUTDOWN`: *"...calls `stop` exactly once on every `Open` Port..., discarding their Errors (A4), and reports `Quiesced`."* Sim Notes: *"quiescence is structural: the report always carries `Quiesced`."* `TRUST-SPAWN`: *"...run-scoped activity is otherwise unwitnessable."* `TRUST-ENV`: bespoke Environment conformance is checked only by *"the conformance trace suite run against it."*
- **Claim:** "Witnesses"/"(witnessed complete)" is used unconditionally, but the shipped Sim Environment has no accounting mechanism analogous to Live's `LIVE-COMPLETION` (per-Slot completion tracking checked before every join) — `SIM-SHUTDOWN` just always sets `Quiesced`, resting entirely on `TRUST-SPAWN`, a Review-only obligation the document itself admits leaves activity "otherwise unwitnessable." The same word appears in the binding Commitment-points table unconditionally, even though for a bespoke Environment its truth is gated only by `TRUST-ENV`, checked once by a conformance suite rather than continuously.
- **Witness:** (a) A `SimPort::start` spawns `std::thread::spawn(|| loop {})` and never joins it — a `TRUST-SPAWN` violation invisible to every Sim mechanism actually specified; `SIM-SHUTDOWN` still reports `Quiesced`, textually indistinguishable from a genuinely clean run. (b) A bespoke `Environment::shutdown` hardcodes `Quiescence::Quiesced` regardless of whether its own spawned activity terminated; nothing in the closed sections lets the Run detect this before `Closed`/`Stopped`. This is mitigated — §0 and the Obligations table already broadly disclose that non-shipped conformance is trusted, not enforced — so it's a wording overclaim on a known, disclosed limitation, not a hidden contradiction.
- **Fix sketch:** Scope the Glossary's "(witnessed complete)" parenthetical to what Live actually accounts for, and note at `SIM-SHUTDOWN` / the Commitment-points `shutdown` row that `Quiesced` beyond Live's join is `TRUST-SPAWN`/`TRUST-ENV`-scoped, matching the hedge the Live Notes already give ("a full witness — every supervised thread was joined").

### CR-03 Sim's `stop()`-hang risk is under-cited relative to Live's parallel case — MINOR, confidence medium, omission
- **Text attacked:** `SIM-START`: *"startup calls `stop` exactly once on the earlier `Open` prefix, in frozen Slot order, discarding those Errors... under `TRUST-SIM-PORT` and `TRUST-SPAWN`, no Port-started run-scoped activity remains."* `TRUST-SIM-PORT`: *"Simulated Ports are deterministic, do bounded `step` work, and carry no hidden authority."* Cf. Live Notes: *"if every completion entry is `Complete` and post-completion teardown violates `TRUST-BLOCKING` by never terminating, `shutdown` remains blocked in a join and produces neither a `ShutdownReport` nor an `EngineExit`... The contract promises no in-process recovery from that trusted nontermination."*
- **Claim:** A `SimPort::stop()` that hangs forever can block `SIM-START`'s partial-startup cleanup or `SIM-SHUTDOWN` exactly as a hung Live teardown blocks `shutdown` — genuinely covered by the generic `TRUST-BLOCKING` obligation ("Ports" generically), not a real specification gap. But `TRUST-SIM-PORT`, the row `SIM-START` actually cites alongside `TRUST-SPAWN`, only mentions bounding `step` work, and no Sim-section Note derives the "the call may simply never return" consequence the way §8's Notes do explicitly for Live.
- **Witness:** A `SimPort::stop` implementation loops forever. `Environment::start`'s partial-failure cleanup path calls `stop` on the already-`Open` prefix and blocks there indefinitely — the same silent-hang outcome as the Live case, but a reader checking `TRUST-SIM-PORT` for this bound finds only "bounded `step` work," with no cross-reference to `TRUST-BLOCKING` and no analogous Derive note acknowledging the stall.
- **Fix sketch:** Cite `TRUST-BLOCKING` alongside `TRUST-SIM-PORT`/`TRUST-SPAWN` at `SIM-START`/`SIM-SHUTDOWN`, and add a short Derive note in §9 mirroring the Live section's.

### CR-04 `LIVE-SUPERVISION`'s shutdown-initiation race has no explicitly named `VERIFY-LIVE` target — MINOR, confidence medium, unenforceable claim
- **Text attacked:** `LIVE-SUPERVISION`: *"The transition out of `Running` and the latch close are one linearized instant (`LIVE-SHUTDOWN`), so every completion is unambiguously premature — publishing atomically with its classification — or expected, staying unpublished (A4)."* `VERIFY-LIVE`'s enumerated properties include *"completion before shutdown remains visible at the close"* and *"a completion concurrent with expiry is classified by the final observation"* — but nothing naming a completion racing shutdown's own *initiating* instant.
- **Claim:** The atomicity `LIVE-SUPERVISION` requires (Running-flag flip + latch close as one instant) isn't unrepresentable in general Rust concurrency, and while §8's Mechanism describes achieving it via a lock ("the lifecycle cell flips and the latch closes under the latch lock, one linearized instant"), that Mechanism section is explicitly nonbinding. `VERIFY-LIVE` names test coverage for the deadline-expiry race and the before-shutdown case explicitly, but the shutdown-*initiation* race (a shell's terminal-guard `Drop` firing exactly as the lock is acquired for shutdown) has no equivalent named bullet, leaving its enforcement tier textually unstated per §0's own promise that every ID is enforced by a named tier.
- **Witness:** A Live implementation flips `Running` and closes the latch as two separate, unsynchronized writes instead of one locked instant; a shell's `run()` returns in the gap. No `VERIFY-LIVE` bullet, read literally, is written to catch specifically this ordering bug.
- **Fix sketch:** Add an explicit `VERIFY-LIVE` bullet: "a completion racing shutdown's own initiating instant is classified as premature or expected, never both/neither."

### CR-06 "Sink failure" silently extends "failure" past the Glossary's own restriction — MINOR, confidence medium, ambiguity
- **Text attacked:** Glossary: *"**fail / failure** — plain English for 'returned an Error'; no further meaning."* Immediately followed by: *"**Sink failure** — a write or flush outcome of: a returned Error (`Interrupted` included), zero progress (`Ok(0)`), or an over-reported byte count."* `JRN-POISON`: *"Any sink failure permanently poisons the Journal... zero progress as `WriteZero`, an over-reported count as `InvalidData`."*
- **Claim:** The base entry restricts "failure" to "returned an Error," with an explicit "no further meaning" clause; "Sink failure," a compound built from that word, is then defined to include two `Ok(n)` outcomes that are not Err returns at all. A reader who applies the base entry's restriction to the compound term would wrongly conclude a zero-progress or over-reported write never poisons the Journal — contradicted by `JRN-POISON`. This is not a real contradiction (each Glossary entry is self-contained per §0's "definition binds vocabulary" rule, and "Sink failure" is fully spelled out in its own line), but the "no further meaning" phrasing sits close enough to invite exactly this misreading.
- **Witness:** Two readings of "Sink failure" both grammatically available: (1) an independent term unconstrained by the adjacent restriction — correct once the whole entry is read; (2) "a failure [as defined above] of the sink," inheriting "no further meaning" and then being surprised `Ok(0)` poisons anything.
- **Fix sketch:** Either drop "no further meaning" from the base entry, or add "(see Sink failure for the write/flush-specific sense)."

### CR-11 `RecordKind::TurnCompleted` conflates Continue-path and Stop-path commit failures — MINOR, confidence medium-high, ambiguity
- **Text attacked:** `pub enum RecordKind { RunStarted, EventAccepted, CommandsPrepared, CommandsDispatched, StopRequested, TurnCompleted }` (one variant, no outcome split); `pub struct JournalFatal { pub record_kind: RecordKind, pub error: JournalError }` (no outcome field). Records table: *"`TurnCompleted` | `outcome` (`Continue`/`Stop`) | End of every non-Fatal turn."* `RUN-FINALIZE`'s two quiescence branches.
- **Claim:** The committed *record* carries an `outcome` field distinguishing Continue/Stop, but `RecordKind` — used inside `JournalFatal`, inside `FatalCause`, inside the typed `EngineExit` — carries no such distinction. A `TurnCompleted(Continue)` commit failure and a `TurnCompleted(Stop)` commit failure (only reachable after a successful `shutdown()` already ran at `StopPending`) both yield `FatalCause::Journal(JournalFatal{record_kind: TurnCompleted, error})`, and `quiescence` doesn't reliably disambiguate them either.
- **Witness:** Run A — an ordinary turn's `TurnCompleted(Continue)` commit fails; `RUN-FINALIZE`'s "Environment unconsumed → call `shutdown`" branch runs a *fresh* `shutdown()` that happens to report `Quiesced`. Run B — a turn answers `Stop`, `shutdown()` succeeds with a clean report, then `TurnCompleted(Stop)`'s commit fails; `RUN-FINALIZE`'s "consumed… → use the retained report quiescence" branch supplies that same `Quiesced` value (guaranteed, since only a clean report reaches this edge attempt at all). Both produce a bit-for-bit identical `EngineExit::Fatal{cause: Journal(JournalFatal{TurnCompleted, e}), quiescence: Quiesced}`, even though Run B's Journal holds a committed `StopRequested` record Run A's doesn't — the typed exit alone can't tell them apart; only re-reading the Journal can, which the document leans on implicitly elsewhere but never states for this case.
- **Fix sketch:** Split the variant into `TurnCompleted(Continue)`/`TurnCompleted(Stop)`, mirroring the record's own `outcome` field.

### CR-12 The shared record-kind marker needs a hand-written `Serialize` the Mechanism prose doesn't disclose — MINOR, confidence high (executed), omission
- **Text attacked:** *"One payload struct per record, each deriving `Serialize`, its first field a kind-typed zero-sized value supplied by the shared `RecordPayload` trait…"* Records example: `{"record_kind":"RunStarted","index":0,"schema_version":1,"logical_time":100}`.
- **Claim:** A plain `#[derive(Serialize)]` on a zero-sized "kind" marker serializes to JSON `null` by default — there's no derive-attribute path to make a unit struct emit an arbitrary string constant — so the shared marker needs a hand-written `Serialize` impl (or `serialize_with`), and the outer field needs `#[serde(rename = "record_kind")]`; neither is disclosed by "each deriving `Serialize`," which reads as applying uniformly to the whole payload including its shared kind field.
- **Witness:** Executed with `rustc 1.96.1`/`serde_json` 1.0.151. Naive code — `#[derive(Serialize)] struct RunStartedTag;` plus `#[derive(Serialize)] struct RunStartedPayload { kind: RunStartedTag, index: u64, schema_version: u8, logical_time: u64 }` — compiles cleanly and prints `{"kind":null,"index":0,"schema_version":1,"logical_time":100}`, not the required format. Adding a hand-written `impl Serialize for RunStartedTag` (`serialize_str("RunStarted")`) plus `#[serde(rename = "record_kind")]` on the field produces exactly `{"record_kind":"RunStarted","index":0,"schema_version":1,"logical_time":100}` — so the mechanism is realizable, just not via a literal, unmodified derive on every part of the payload.
- **Fix sketch:** State that the shared kind-marker's `Serialize` is one hand-written impl driven by `RecordPayload`'s tag, distinct from the "each deriving `Serialize`" that applies to the payload structs themselves.

### CR-13 `RUN-FINALIZE`'s fatal-path `shutdown` call cites no termination obligation — MINOR, confidence medium, omission
- **Text attacked:** `RUN-FINALIZE`: *"`start` returned Ok and the Environment is unconsumed → call `shutdown`, take the report's quiescence, and discard the report's Error (A4: a cause exists)…"* Cf. Live Notes: *"if… post-completion teardown violates `TRUST-BLOCKING` by never terminating, `shutdown` remains blocked in a join and produces neither a `ShutdownReport` nor an `EngineExit`… The contract promises no in-process recovery from that trusted nontermination."*
- **Claim:** `RUN-FINALIZE` is a Run-level guarantee applying uniformly to both Environments, and implicitly assumes this fresh `shutdown()` call returns — but the only textual backing (`TRUST-BLOCKING`) is disclosed solely in §8's Live-specific Notes, never cited at `RUN-FINALIZE`'s own row, even though §0 explicitly exempts "trust marks pointing into the Obligations table" from its backward-citation rule (so `RUN-FINALIZE` could cite it directly with no ordering problem). - **Fix sketch:** Cite `TRUST-BLOCKING` at `RUN-FINALIZE`'s "call shutdown" clause directly.

### CR-14 `Context::remaining()` conflates "exactly full" with "overflowed" — MINOR, confidence high, ambiguity
- **Text attacked:** `remaining()` doc comment: *"Exact Commands the batch can still store; zero once the overflow marker is set."* Mechanism: *"`remaining()` is capacity minus length, or zero when the marker is set."*
- **Claim:** `remaining() == 0` is produced by two disjoint states — buffer exactly full with nothing lost, versus full *and* at least one further `emit` silently dropped (`APP-OVERFLOW`) — and `Context`'s public API (`index`, `logical_time`, `remaining`, `emit`) has no accessor distinguishing them. Practical impact is limited (`emit` stays infallible either way, and the Core-level consequence is only visible after the handler returns, not through `Context` mid-turn), but the conflation is directly demonstrable from the text alone.
- **Witness:** Capacity 3: three `emit` calls append, `remaining() == 0`, marker unset. A fourth `emit` (over capacity): marker set, nothing stored, `remaining()` still reads 0 per the Mechanism's own "or zero when the marker is set" clause — observationally identical through every public method `Context` exposes.
- **Fix sketch:** Expose `overflowed(&self) -> bool`, or state explicitly that `remaining()` doesn't distinguish the two cases by design.

## NIT-level findings

### CR-07 `TurnOpen` used as both a bare marker and a generic marker in the nonbinding transition table — NIT, confidence medium, ambiguity
- **Text attacked:** Enforcement table: `Initial → run_started() → TurnOpen at index 0`, then `TurnOpen<A> → no_commands(...) → EffectsComplete<A>` and `classify(answer) → ClassifiedTurn::Continue(TurnOpen<Continue>) or ClassifiedTurn::Stop(TurnOpen<Stop>)`. `Certificate<W: std::io::Write, P>` is declared with one phase parameter `P`.
- **Claim:** Literally, "`TurnOpen`" cannot be simultaneously a non-generic marker (produced by `run_started`) and a generic marker of arity 1 (`TurnOpen<Continue>`, consumed by `classify`) without an unstated default parameter (`struct TurnOpen<A = Unrefined>;`), which the document never introduces. Same pattern for `Checkpointed`/`Checkpointed<Continue>`/`Checkpointed<Stop>`.
- **Witness:** Two conforming realizations diverge (reasoned, not executed): (a) `struct TurnOpen<A = Unrefined>;` reused for both — realizable via Rust default type parameters; (b) wholly separate marker types (`TurnOpenContinue`, `TurnOpenStop`) with the table's notation read as shorthand — equally realizable. Both satisfy every *binding* row (`RUN-GRAMMAR`, `RUN-ENFORCEMENT`); the ambiguity lives entirely inside a table the document itself flags as *"neither an API block nor a binding table,"* so no binding claim breaks — only a reader trying to render it literally is confused.
- **Fix sketch:** Show the default-parameter declaration once, or rename the refined states to avoid the arity-overload appearance.

### CR-08 `DET-ENV`'s Quiescence-equality clause reads falsely without the Trace glossary entry — NIT, confidence medium, ambiguity
- **Text attacked:** `DET-ENV`: *"equal traces produce equal handler calls, ... and exits equal in every Core-owned discriminant and payload — ... and `Quiescence`."* Glossary, **Trace**: *"every Environment operation's returned value — Ok payloads and the `ShutdownReport` included..."*

### CR-16 `RUN-ENFORCEMENT`'s citation for `RUN-INDEX`'s overflow-panic clause is ambiguous between two different assertions — NIT, confidence medium, ambiguity
- **Text attacked:** `RUN-INDEX`: *"…checked before `next_event`: at certificate index `u64::MAX` the run ends `Core(IndexExhausted)` with no candidate consumed. Overflow past that check is an invariant panic."* `RUN-ENFORCEMENT`'s Derive note: *"the index arithmetic behind `accept_event`, backed by one always-on assert — a freshly minted certificate sits at the start index."*
- **Claim:** "A freshly minted certificate sits at the start index" reads naturally as describing the one-time `Initial` certificate at Run startup (index 0), not a per-turn guard on `accept_event`'s increment arithmetic — yet it's the only always-on assertion `RUN-ENFORCEMENT`'s "three runtime points" inventory names anywhere near "the index arithmetic behind `accept_event`." Tracing the graph shows the arithmetic is provably safe regardless of how the citation is read (the domain check at `BetweenTurns` runs strictly before the derived increment, so index can never exceed `u64::MAX` in practice), so this is a citation-clarity gap, not a soundness risk.
- **Witness:** index = `u64::MAX - 1` → passes the check → `EventAccepted` commits → index = `u64::MAX` → the next `BetweenTurns` entry's domain check catches it before deriving any further increment; no reachable call site runs the increment arithmetic starting from `u64::MAX`.
- **Fix sketch:** Name the concrete per-turn assertion site distinctly from the startup-certificate one, or clarify "a freshly minted certificate" is meant to cover every `accept_event`-minted successor, not just `Initial`.

### CR-17 "Fatal" names both the run-level classification and a per-handler request that doesn't always become one — NIT, confidence medium, ambiguity
- **Text attacked:** Glossary: *"**Fatal** — the run-level classification of the Error or Core condition that ended the run."* `Outcome::Fatal(E)`. `TurnOpen` Phases row: *"overflow marker set → discard the batch → `Core(CommandBoundExceeded)`, beating every `Outcome`… a returned `Fatal` payload is discarded with the batch (A4's cleanup rule)."*
- **Claim:** The word names two distinct things — the Glossary's run-level classification, and `Outcome::Fatal(E)`, a per-handler *request* that the run become Fatal. ### CR-18 "a transition *is* a commit" overstates relative to the two recordless edges — NIT, confidence medium, ambiguity
- **Text attacked:** §7 intro: *"Phases carry the work; edges carry the records; a transition *is* a commit — the next phase is unreachable until the edge's record commits."* Edges table: *"The two recordless edges commit nothing and cannot fail."*
- **Claim:** Taken literally, the opening claim is contradicted 130 words later by the two recordless edges, which explicitly "commit nothing." It survives only under the general Commitment-point sense (A3), not the Journal-commit sense its own next clause invokes. Scene-setting prose, not itself a binding rule — deleting it changes no obligation per §0's own deletion test — so the imprecision is harmless, but a careless reader hits an apparent contradiction on the section's first page.
- **Fix sketch:** "a transition is a commitment point — the next phase is unreachable until the edge's record, where the edge carries one, commits."

### CR-19 Cross-source publication-race resolution is authorized only in §7, despite §5's completeness claim — NIT, confidence medium, omission
- **Text attacked:** §5: *"This section is the complete contract: an implementation satisfying every row here, under `ENV-SERIAL`'s call pattern, is a conforming Environment."* §7 Notes: *"*Derive:* an Environment may resolve races among concurrent sources however it likes; the accepted trace records the resolution, and `DET-RUN` holds conditional on it."*
- **Claim:** §0's own placement rule states "a fact any conforming Environment implementor would need lives in the contract" — a bespoke Environment author, directed by §5's completeness claim to read only §5, wouldn't learn there that they're free to resolve races between two concurrently-failing sources however they like; that authorization appears only as a Derive note in §7, a later section meant to build on the contract, not extend it. `ENV-LATCH` itself only pins one publication's order relative to one *observation call*, never who decides when two publications race *each other* to become "the first" for A4's purposes.
- **Witness:** A bespoke Environment implementor reading only §5 to confirm conformance has no textual basis there for handling two Ports failing "simultaneously" — the freedom exists, but only in §7's prose.
- **Fix sketch:** Add one clause to `ENV-LATCH` itself authorizing this freedom.
