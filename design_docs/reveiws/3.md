Tier 1 — the design is wrong or missing something

1. A clean Stopped exit can hide a real Port failure — and A4 does not license the discard

RUN-CHECKPOINT (674) puts the last latch observation before the completion record; ENV-LATCH (396) makes shutdown close the latch and discard a pending Error.

Trace: turn N answers Stop, empty batch → checkpoint take_error → None → witness minted. StopRequested commits (a real write+flush — the window is milliseconds). In that window an Execution Port's run returns Err; lifecycle is still Running, so per LIVE-SUPERVISION (816) this is a runtime failure, not shutdown work — latch goes pending. StopPending calls shutdown → latch closed → Error discarded. Thread already finished → joined → Quiesced → TurnCompleted(Stop) → EngineExit::Stopped { state }.

The run reports success. For the intended tched my flatten-position orders and stopped cleanly" while the execution Port was dead. The nearest mitigation — reading terminal Port state through a user-owned handle (855–858) — is Live-only and undocumented as a mitigation.

The justification is also unsound. A4 (114run observes is the Fatal cause. Everythingafter is best-effort cleanup" — "after" presupposes a first Error. On a clean Stop there is none, so A4 authorizes nothing, yet it is cited at three discard sites (408, 819, 919). Fix must decide: either one more latch observation between StopRequested and shutdown (making it Fatal), or A4 gains a second clause covering post-Stop errors and Stopped is documented as forfeiting them. Silence is what makes it a hole rather than a policy.

2. The commitment-point definition is too strong, and the Sim violates it at start

Glossary (91–92): "Before it, nothing happened; after it, nothing is retried, revoked, or rolled back." Three normative statements collide with it:

- JRN-COMMIT falsifies it directly. Write succeeds, flush fails → a complete, well-formed record line is
permanently in the sink, and JRN-COMMIT (4rm complete lines"). Commitment neverreached; "nothing happened" is false.
- Sim start revokes its own commitment. The table (384) names the commitment "Activation: run-scoped activity becomes live"; SIM-START (913) places it before the first Port start; ENV-START (395) then requires teardown on Err. So: commit → B.start fails → stop(A) → activity no longer live. LIVE-START (818) puts the commitment after all fallible work. The same table row therefore sits on opposite sides of the failure boundary in the two shipped
implementations, and the preamble's "the r only witness" (379) is false for startalone.
- Sim next_event passes its point of no reate exists. SIM-SELECT advances now, clearsthe arm, spends budget, then calls step, which may Err. Literally "no candidate was consumed" — but the run's time authority moved irreversibly and the arm is gone, and no commitment row covers that, contradicting the tables-are-exhaustive rule (23). The Note at 934–936 defends this by analogy to on_command(Err), but that analogy is inverted: dispatch's commitment precedes the Port call, next_event's follows it. (Blast radius is small — ENV-SERIAL allows only shutdown afterward — but the row is untrue.)

Fix: restate the definition as "the instant after which the operation's outcome is fixed", let each Err column say what the failing call leaves permanently changed, then re-derive SIM-START and SIM-SELECT against it.

3. SIM-SHUTDOWN contradicts SIM-START on a call sequence ENV-SERIAL permits

SIM-START (913): the failing Port's Err ends its lifecycle and "no further call, stop included, reaches it." SIM-SHUTDOWN (919): calls "every Port's stop." ENV-SERIAL (394) permits shutdown after any Err.

Slots P0/P1/P2; P0.start→Ok, P1.start→Err,ops P0, returns Err. A conforming callerthen calls shutdown → P0 gets a second stop, P1 gets a forbidden stop, P2 gets stop without start — a sequence SimPort never defines. The Run itself is safe (startup step 2 at 595 skips shutdown), but §5 judges conformance under ENV-SERIAL's pattern, not the Run's, and the conformance suite is the certification instrument. LIVE-SHUTDOWN (819) has the same shape against LIVE-START's already-joined shells.

Fix: scope SIM-SHUTDOWN to Ports whose lifecycle has not ended, define stop-without-start, or have ENV-SERIAL forbid shutdown after a start Err.

4. Two missing sizing obligations turn healthy runs Fatal

BOUND-SIZING (1023) exists precisely to relate two configured bounds. Two structurally identical relations got no row:

- Per-Port inbox capacity vs max_commands_per_turn. max_commands_per_turn = 64, Execution inbox = 8, handler emits 64 Commands to Execution, Engine dispatches in a tight loop without yielding. Position 8 → inbox full → Environment(Dispatch { position: 8 }), Fatal, 56 Commands discarded, RUN-FINALIZE shuts down and the wedged Port likely misses the deadline → Incomplete → obligation 1022 demands the process be killed. Transient backpressure escalates to process death. Note capacity ≥ batch is not sufficient — it needs a drain-rate assumption across turns.
- BOUND-SIZING ignores the Event payload. It sizes max_record_bytes for "the largest batch stageable", but EventAccepted carries the whole event (653) plus framing. One oversized inbound Event → BoundExceeded → Fatal, with the candidate already consumed for good and no record of it anywhere. Unlike the batch, the Application cannot bound its input.

Fix: restate BOUND-SIZING over the largest record, and add the inbox/max_commands_per_turn/drain-rate relation.

5. Live has no termination story — and theds is unreliable

Four independent pieces, one hole:

- offer destroys the Event it rejects. offer(&mut self, event: C::Event) -> Result<(), OfferRejected> takes by value; OfferRejected (803) carries no payload. LIVE-EVENTS (812) says the Port "may recover" — but it cannot retry that Event; it's gone.
- So the finite-source pattern can hang the run. The terminal Event (337–340) is the only documented route to a normal live end. Engine is inside a long handler → queue fills → source Port offers its terminal Event → Full →
Event destroyed → Port parks awaiting the  next_event, waits forever. BOUND-LOOPS(137) explicitly declines to bound that wait.
- No live analogue of SIM-COMPLETION. Sim answers "nothing can arrive" with a typed Error (918); Live blocks. A zero-Port live Environment is constructible (SIM-START's parenthetical proves the doc contemplates zero Ports; nothing requires the set nonempty) and hangs unconditionally.
- recv's post-signal semantics are unpinned, and that undermines the Run's own advice. LIVE-LIFECYCLE (817) says recv reports the signal "ahead of" queued Commands — once-then-drain, or forever? Under "forever", this happens: the Run's derive at 756–758 tells an Application wanting stop-specific Port behavior to emit it as Commands before answering Stop. Handler emits Flush, answers Stop. dispatch admits it — handoff "stands" per the commitment table. Port is blocked in recv; shutdown raises the signal; recv returns Shutdown; the canonical loop { match recv() {…} } Port breaks and returns. Flush is guaranteed never seen, and the Port never chose to abandon it. ENV-SHUTDOWN permits abandonment, so it isn't a contradiction — but the recommended mechanism is unreliable and nothing says so.

There is also no external cancellation of any kind: Engine::run(self) blocks with no handle, so SIGINT must be modeled as a Port. That's a fine answer; the doc never states it.

Fix: pin recv's second-and-later returns; give offer either a lifecycle-cancellable waiting form or return the Event in OfferRejected; add an Obligations row for Full recovery and for inbox draining; reject an empty Port set or give Live a typed "nothing can arrive" for the decidable case.

6. The Environment contract is not complete enough to certify a bespoke implementation

§5 claims to be "the complete contract" and §12 says the conformance suite is a bespoke Environment's certification. Three things a conforming implementation can get wrong:

- No liveness obligation on the latch. ENV-LATCH binds only what happens if a pending Error is observed. Nothing requires a blocked next_event to return when the latch goes pending. LIVE-SELECT (813) states it; the contract does
not. A bespoke Environment can park on itstable Error, forever, violating no row.
- No Sim row realizes ENV-TIME, and nothing binds the returned Timestamp to now. LIVE-TIME (814) names ENV-TIME; §9 has no counterpart. A sim built strictly to §9 can return from_nanos(0) for every candidate while now marches to
5000 — satisfying ENV-TIME (nondecreasing)irtual time is invisible to the Applicationand to logical_time. The nondecrease that does hold rests on an unstated invariant ("every armed time ≥ now", from SIM-WAKEUP + min-selection) that LIVE-TIME states structurally and §9 never states at all.
- Neither selection row names next_event's commitment point, though the table demands "each names its own" (379). LIVE-DISPATCH, SIM-DISPATCH, LIVE-START, SIM-START all do. The Live instant exists only in Mechanism prose (842), which §0 says is not binding — so nothing stops an implementer from stamping after the dequeue, which would let a
time-conversion failure return Err with a

Related: the live Error sum enumerated at 959–960 has no thread-spawn failure variant, though the start step table's step 2 is the spawn and step 4 says "any failure so far" returns Err. An implementer using bare thread::spawn gets a panic → abort → an outcome ENV-START cannot represent. (And "queue exhaustion" is ambiguous — the fan-in queue's Full goes to the Port, never to the Environment, so only the dispatch inbox produces it.)

7. RUN-GRAMMAR claims compile-time enforcement it does not have, and the honest-boundary list doesn't disclose it

The row says "a wrong TurnCompleted outcome, a wrong index, a skipped checkpoint … fails to compile." Against the actual mechanism:

- Wrong outcome is a free runtime choice. EffectsComplete is one phase; complete_continue and request_stop take the same witness type. Calling complete_continue after a Stop answer compiles, commits TurnCompleted(Continue), and silently discards the Application's Stop. The defense at 717 ("TurnOutcome is chosen by the transition") only stops a wrong payload field, not a wrong method.
- commands_dispatched() takes no argument, so committing it after a partial dispatch compiles and writes a record whose stated meaning ("Every prepared Command was handed off", 655) is false. No assert covers it, and the record has no payload for a golden test to see.
- A wrong index cannot be a compile error — it's a runtime u64 derived inside accept_event, backed by one assert. The true claim is "no transition takes an index parameter".
- The witnesses carry no turn, token, or ordering identity. Affinity bounds spending at one, not minting. Mint two checkpoint witnesses in turn N, spend the spare in turn N+1 → N+1 skips its checkpoint and compiles. Mint the checkpoint before prepare_commands and spend it after commands_dispatched → satisfies the edge while violating "after its last handoff". Call the shutdown helper before request_stop → StopRequested commits after the Environment is down, inverting the record table's "before shutdown" (656) and A5, while complete_stop still type-checks.
- "Possession of the token in phase S provalse. Only edge-detected failures consumethe token. Every state-detected Fatal — Application, Dispatch, NextEvent, Checkpoint, all four CoreErrors — happens with the token alive. The Notes' "After any Fatal, no commit is expressible: the token is gone" (741) assumes a
drop the compiler never forces.

The honest-boundary list admits only omission; every item above is commission. Your own ledger's B7 disposition says payload content is assert/test territory — the row drifted past that. Tellingly, the compile-fail suite (1034) promises coverage for exactly the three clauses that are real compile errors.

Fix (and it's cheap): fold both witnesses into phases — EffectsComplete --checkpoint--> Checkpointed, StopPending
--shutdown--> Quiesced — and parameterize fectsComplete<Continue>/<Stop>, carried byno_commands/commands_dispatched). Token consumption then does the counting and the ordering, the free-standing affine values disappear, and the claims become true instead of softened.

8. Determinism is the headline property and it rests on nothing

- No axiom implies it. §2 says "Everything in this document is a consequence of eight axioms"; none of A1–A8 mentions determinism, reproducibility, or trace equivalence. DET-RUN/DET-ENV are free design choices presented as derived — so nothing in the axioms constrains a future edit that weakens them.
- The equivalence relation lives in a Glossary bullet. The Trace line (99–101) alone fixes what both guarantees quantify over. Change that bullet and both guarantees change strength. That's guarantee content, not vocabulary.
- DET-ENV has no held-fixed antecedents. DET-RUN names them ("same build, Application, initial State, configuration, and trace"); DET-ENV names none. Read literally: same App, initial State 100 vs 200, identical Event/Timestamp/operation/sink sequences → equal traces, different Journal bytes. The doc's own "stands alone" discipline forbids importing the antecedents.
- The Trace's first clause is redundant or the rows are false. If "every Environment operation result" means the full return value, Ok((Event, Timestamp)) already contains the accepted sequence and clause 1 is dead text. If it doesn't, here's a counterexample: two runs whose EventAccepted commit fails at encode — one with a 300-byte event (BoundExceeded), one with a non-string map key (Encode). Neither candidate is ever accepted, so neither value is in the trace; no sink operation occurs in either. Same trace, different JournalError variant, which DET-ENV pins.
- The certification comparator is under-enumerated. §12 makes DET-ENV's list the definition of the conformance comparator. It omits the EngineExit variant itself, Fatal.quiescence, and — by attaching "including payloads" only to CoreError — Dispatch { position }, the very field 660 relies on. A bespoke Environment returning Incomplete where the reference returns Quiesced, or position: k+1, certifies clean.
- The Application-determinism check is vacuous. Obligation 1013 is verified by "same trace twice → identical Journal bytes and exit". The trace is an output. An on_event that reads the clock and emits one Command on even nanos, none on odd, produces different traces — antecedent fails, check reports nothing, hidden clock undetected. The procedure only catches length-preserving nondeterminism. It must name an input held fixed: "two runs against
the same scripted Environment and sink".

Also: DET-RUN's "exactly equal" tail is not expressible — JournalError holds serde_json::Error and io::Error, neither PartialEq. And "Only Error values inside the exit may differ; they are erased from the trace" is false for FatalCause::Application(AE) and JournalError::Encode, which were never in the trace and are in fact determined.

9. A Fatal turn hands back a half-applied

A4's "Failure" paragraph (120–122) says consequences of no-rollback "appear once, at each effect's owner." The Journal's appear (JRN-COMMIT); the Environment's appear (commitment table). State's do not. §3 has no such note, yet: a handler mutates State to record "orders sent", emits past capacity, and the batch is discarded → Core(CommandBoundExceeded) with EngineExit::Fatal { state } claiming orders that never left the process. Same for Outcome::Fatal after mutation, and for a failed CommandsPrepared commit. Nothing classifies State mutation as an effect or gives it a commitment point.

10. Two Journal-boundary classification errors

- JRN-SINK's positioning rule is unenforceable but classified as enforced. "A sink is fresh for one run or positioned immediately after a newline" — std::io::Write exposes no position, and Engine::new takes any W by value. It is absent from the Obligations table, which §0 says means "enforced, not assumed". Append to a file whose previous writer was SIGKILLed mid-line and JRN-FORMAT's "line order is the sequence" and RUN-RECORDS' "every nonempty Journal begins with a versioned record" both become false. Same hole for a second handle to the same sink — Journal::new and commit are public, so a second Journal can interleave. (Three independent angles hit this one.)
- JRN-POISON's panic is reachable from the public API. Journal and commit are public, and the doc explicitly serves "direct Journal consumers with arbitrary payloads" (490). A consumer that ignores is_poisoned() gets a process abort — which A8 classifies as a bug in Kavod, contradicting A8's own "a failing user component reports a typed Error". Every other panic in the doc is genuinely internal. Fix: return JournalError::Poisoned publicly, keep the
assert on the Engine's private path.

What I attacked and could not break

Phase-graph totality (all 9 TurnOpen combinations, all 7 states, all 15 Fatal sites → RUN-FINALIZE assigns exactly one quiescence to each; EngineExit is total). RUN-INDEX's "accepted count" vs index 0 — consistent, and the IndexExhausted boundary is exact with the overflow panic provably unreachable. Journal bound arithmetic — every size from max_record_bytes to +2 lands in exactly one rejection, step 4 is reachable, nothing slips through. Poison-panic unreachability for the Run — every edge failure destroys the Journal with the token. CommandsPrepared + Dispatch { position } really does identify the handed-off prefix in every failure mode including the sim's Ok-while-latching. Error erasure from the trace is genuinely sound — no erased value influences control flow, records, operation counts, or the reported EnvironmentOperation. PhantomData<fn() -> S>'s auto-trait rationale is correct. Never, the ports! expansion, the type threading through Engine/Environment/Application/Context, and the borrow structure all check out. Heterogeneous Port storage is open-by-design, not unsatisfiable. SIM-WAKEUP cross-arming, sim now monotonicity across all four paths, and the self-re-arming step loop are all closed. Live: gate/cancel races, clock races, take_error atomicity, detached-straggler safety under forbid(unsafe_code), and premature-closure-vs-shutdown races are all either unobservable or correctly delegated to Obligations rows.

Two agent claims I dropped after checking: a "lost wakeup" in LIVE-SELECT (the mechanism does route fan-in wakes through the latch, 825, and LIVE-SELECT binds the wait's termination condition), and "a record whose kind disagrees with its payload isn't a compile error" (it's unrepresentable-by-construction, which is §0's top tier anyway).
